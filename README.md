# מערכת ניהול מחזור חיי נסיעה

מימוש **שלבים 1–4** מסעיף 11 באפיון: תיק, נוסעים, רכיבים, מנוע אבני הדרך,
מסך "היום", תקשורת וואטסאפ, ציר הזמן של כל התיקים, פאנל הכספים ועמוד הלקוח.

זה כל מה שסעיף 12 מגדיר כ-v1. מה שנשאר הוא שלב 5: תבניות ספורט וקרוז,
וקליטה אוטומטית של פרטי טיסה.

## הרצה מקומית

צריך PostgreSQL. הכי פשוט דרך Docker:

```bash
docker run -d --name flyapp-db -p 5432:5432 \
  -e POSTGRES_USER=fly -e POSTGRES_PASSWORD=fly -e POSTGRES_DB=flyapp postgres:16
```

ואז:

```bash
npm install
cp .env.example .env          # ולמלא את המפתחות, ראו למטה
npm run db:migrate            # יצירת הטבלאות
npm run db:seed               # שלושה תיקי הדגמה (אופציונלי)
npm run dev                   # http://localhost:3000
```

ליצירת `SESSION_SECRET` ו-`PASSPORT_ENCRYPTION_KEY` (כל אחד בנפרד):

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

`APP_PASSCODE` היא הסיסמה המשותפת לשניכם. בפרודקשן היא חייבת להיות באורך
12 תווים לפחות, אחרת השרת לא יעלה.

פקודות נוספות:

```bash
npm test          # 192 בדיקות יחידה
npm run typecheck
npm run db:studio # דפדפן למסד הנתונים
npm run job:daily # ה-job היומי מהטרמינל

# נתוני עומס — 120 תיקים פרוסים על עונה שלמה
npm run db:seed:bulk -- 120

# בדיקת מוכנות מול פריסה חיה
npm run preflight https://your-app.vercel.app <DAILY_JOB_TOKEN>
```

## העלאה לאוויר

**המדריך המלא צעד-אחר-צעד נמצא ב-[DEPLOY.md](./DEPLOY.md).** בקצרה, שתי דרכים. **בחרו אחת ומחקו את הקבצים של השנייה** — אין טעם להחזיק את שתיהן.

### א׳ — Vercel (מומלץ)

הכי פחות תחזוקה, ו-Next.js רץ שם באופן טבעי.

1. **מסד נתונים.** פתחו פרויקט ב-[Neon](https://neon.tech) (יש שכבה חינמית
   שמספיקה בקלות). קחו משם שתי כתובות: את זו של ה-pooler ואת החיבור הישיר.
2. **ייבוא הרפוזיטורי** ל-Vercel. הוא יזהה Next.js לבד.
3. **משתני סביבה** (Settings → Environment Variables), כולם ל-Production:

   | משתנה | ערך |
   | --- | --- |
   | `DATABASE_URL` | כתובת ה-pooler של Neon |
   | `DIRECT_DATABASE_URL` | החיבור הישיר של Neon |
   | `APP_PASSCODE` | הסיסמה המשותפת, 12 תווים ומעלה |
   | `SESSION_SECRET` | 32 בתים ב-base64 |
   | `PASSPORT_ENCRYPTION_KEY` | 32 בתים ב-base64 |
   | `DAILY_JOB_TOKEN` | מחרוזת אקראית ארוכה |
   | `CRON_SECRET` | אותו ערך כמו `DAILY_JOB_TOKEN` |
   | `AGENT_NAME` | השם שחותם על ההודעות ללקוחות |
   | `AGENCY_NAME` | שם העסק |
   | `AGENT_EMERGENCY_PHONE` | מספר החירום שנשלח לפני היציאה |
   | `HOST_AGENCY_FEE_RATE` | הנתח שהסוכנות המארחת גובה מההפרש, למשל `0.01` |
   | `HOST_AGENCY_NAME` | שמה, לתצוגה בפאנל הכספים |
   | `PUBLIC_BASE_URL` | הכתובת הציבורית של המערכת, בלי לוכסן בסוף |

4. **Deploy.** סקריפט `vercel-build` מריץ `prisma migrate deploy` לפני הבנייה,
   כך שהטבלאות נוצרות מעצמן.
5. **ה-cron כבר מוגדר** ב-`vercel.json` — 03:30 UTC, כלומר 06:30 בחורף ו-06:30
   בקיץ שעון ישראל. במסלול Hobby מותר cron אחד ביום; אם אתם ב-Pro, אפשר לצופף.

`Dockerfile` ו-`fly.toml` מיותרים במסלול הזה.

### ב׳ — Fly.io או כל מקום שמריץ קונטיינר

```bash
fly launch --no-deploy
fly postgres create                    # ואז: fly postgres attach <שם>
fly secrets set APP_PASSCODE=... SESSION_SECRET=... \
                PASSPORT_ENCRYPTION_KEY=... DAILY_JOB_TOKEN=...
fly deploy
```

`fly.toml` כבר מגדיר `release_command` שמריץ את המיגרציות לפני שהגרסה החדשה
מקבלת תעבורה, ובדיקת חיים מול `/api/health`.

מה ש-Fly לא נותן לבד הוא cron. אפשר מכל מתזמן חיצוני:

```bash
curl -X POST https://<האפליקציה>.fly.dev/api/jobs/daily \
     -H "Authorization: Bearer $DAILY_JOB_TOKEN"
```

`vercel.json` מיותר במסלול הזה.

### אחרי הפריסה, בכל מסלול

1. היכנסו ל-`/` — אתם אמורים להיות מופנים ל-`/login`.
2. הריצו את ה-job ידנית פעם אחת עם ה-curl שלמעלה, ותראו שהוא מחזיר JSON.
3. פתחו תיק אמיתי אחד וראו שאבני הדרך נוצרות במועדים שנראים לכם נכונים.

## מה קנה המידה לימד

הסוכן אמר 100+ תיקים פעילים בשיא העונה (סעיף 13.1). בניתי סקריפט שמייצר 120
תיקים פרוסים על עונה, והרצתי מולו את המסכים. זה שינה כמה החלטות שנראו בסדר
עם שלושה תיקי הדגמה:

**מסך היום התפוצץ.** עם שלושה תיקים היו 20 פריטים; עם 123 היו 500 — וזה היה
הקאפ, כלומר המסך גם הציף וגם חתך בשקט. שתי הפרות: סעיף 14 אומר שב-30 פריטים
הסוכן מתעלם, וסעיף 12 אומר שאף אבן דרך שעברה מועד לא נעלמת. התיקון:

- שאילתה נפרדת לכל קבוצה, כך שאף קבוצה לא נדחקת החוצה על ידי אחרת, וחציית
  תקרה מדווחת על המסך במקום להיחתך בשקט.
- "עד סוף השבוע" מגיע למאות פריטים בקצב יציב, ולכן הוא מקובץ לפי יום ומתקפל.
  הוא תצוגה מקדימה, לא רשימת מטלות.
- "נולדו באיחור" מקובץ לפי תיק ולא לפי אבן דרך. ככה באמת סוגרים אותן: פותחים
  את התיק פעם אחת ועוברים על כולן בהקשר.

**המיון היה שגוי.** התור היה ממוין לפי מועד אבן הדרך, כלומר הישן ביותר קודם —
ולרוב זו דווקא הצעת ביטוח לתיק שיוצא בעוד חודשיים. מה שבוער הוא דרכון של מי
שטס בעוד שלושה ימים. התור ממוין עכשיו **לפי קרבת הטיסה**, כי עלות הפספוס גדלה
ככל שמתקרבים ליציאה. אם נגמר לסוכן היום, מה שנשאר למטה הוא מה שיש עליו זמן.

**מועדי ביטול המשיכו לצעוק אחרי ההמראה.** אי אפשר לבטל נסיעה שנמצאת באוויר,
ולכן ה-job היומי סוגר אבני דרך של ביטול חינם ברגע שהתיק יוצא לדרך. הן נסגרות
כ"נדחו" עם סיבה ולא נמחקות, כי החשיפה הכספית היא חלק מההיסטוריה. מועד תשלום
לספק לעומת זאת נשאר פתוח — החוב לא נעלם עם ההמראה.

**בציר הזמן כל שורה הייתה אדומה.** הספירה ערבבה איחור אמיתי עם אבני דרך
שנולדו באיחור, ואז כל תיק קיבל תג אדום. סעיף 4 אומר שצבע הוא מידע, וכשהכל
אדום שום דבר לא אדום. עכשיו הן נספרות בנפרד ונצבעות אחרת.

זמן טעינת מסך היום ירד מ-1.6 שניות ל-166 אלפיות.

## ציר הזמן של כל התיקים

כיוון הזמן מימין לשמאל, כמו קריאה בעברית: העבר הקרוב בקצה הימני והעתיד נמשך
שמאלה. עמודת השמות מוקפאת — בלעדיה, ברגע שגוללים בטלפון כבר לא יודעים על מי
מסתכלים.

כל תיק הוא שורה: משולש מסמן את יום הטיסה, פס אפור את משך הנסיעה, ונקודות
צבעוניות את אבני הדרך הפתוחות. נקודות באותו יום מתמזגות לאחת בצבע החמור
מביניהן, אחרת הציר הופך לרצף נקודות חופפות.

סינון: חיפוש לפי לקוח, יעד או מספר תיק; "רק בוערים"; חלון של 30, 90 או 180
יום; וסטטוס. העימוד הוא 40 תיקים לעמוד.

## כסף

מודל ההכנסה שאומת מול הסוכנים:

1. **מתמחרים מעל עלות הספק ומרוויחים את ההפרש.**
2. **הסוכנות המארחת גובה נתח מההפרש** (לא מהמחזור). ברירת המחדל אחוז אחד.

מכאן נובע שהרווח אינו שדה שמזינים אלא חישוב. שדה "עמלה" לצד מחיר ועלות היה
מקור אמת שני שמתפצל מהראשון ברגע שמישהו מעדכן מחיר ושוכח לעדכן עמלה — וסעיף 4
אומר במפורש שהזנה ידנית היא אויב המערכת.

מה שכן משתנה אחרי הנסיעה הוא **העלות**: ספק מוסיף חיוב, רכיב מבוטל, שער מטבע
זז. זו גם התשובה לשאלה למה סעיף 7א מגדיר אבן דרך שנפתחת 30 יום אחרי החזרה —
מה שמזינים בה הוא העלות האמיתית, והרווח בפועל נגזר ממנה.

| שדה | מקור |
| --- | --- |
| מחיר ללקוח | מוזן בפתיחת התיק |
| שולם | מתעדכן לאורך הדרך |
| עלות ספקים משוערת | מוזנת בפתיחת התיק |
| עלות ספקים בפועל | מוזנת באבן הדרך שנפתחת אחרי החזרה |
| שיעור נתח הסוכנות | נשמר על התיק בעת יצירתו, מ-`HOST_AGENCY_FEE_RATE` |
| ברוטו, נתח הסוכנות, נטו, הפער בין צפוי לבפועל | **מחושבים** |

**המספר הראשי הוא הנטו**, אחרי הנתח. ברוטו לבדו הוא מספר שמשקר כלפי מעלה.
על הפסד לא נגבה נתח, ולכן החישוב לא "מקטין" הפסד בטעות.

שיעור הנתח נשמר על כל תיק ולא כקבוע גלובלי. אם תסגרו אחוז אחר בשנה הבאה,
הנתונים של העונה שנסגרה לא ישתנו מתחתיכם.

אבן הדרך "סגירת הרווח בפועל" היא אחת משתי אבני הדרך שהכפתור שלהן לא מסמן
"בוצע" אלא פותח קלט: כאן סכום, ובביטוח הכרעה בין נרכש, סורב או חיצוני.
היא גם נסגרת לבד אם העלות בפועל הוזנה מפאנל הכספים.

זו לא הנהלת חשבונות. סעיף 3 מוציא אותה מ-v1 במפורש: אין חשבוניות ואין מע"מ.

## הודעות וואטסאפ

סעיף 9 קובע שב-v1 **אין** אינטגרציה ל-WhatsApp Business API: היא דורשת אישור
תבניות, עולה כסף לכל הודעה, ולוקחת זמן. במקום זה המערכת מכינה את הנוסח,
והכפתור פותח את וואטסאפ עם ההודעה מוכנה. הסוכן לוחץ שלח.

### איך זה עובד בפועל

במסך "היום", אבן דרך שפונה ללקוח מציגה כפתור ירוק **וואטסאפ** במקום "בוצע".
לחיצה עליו פותחת את הנוסח, ניתן לעריכה אחרונה, עם הטלפון של הלקוח. משם:
**פתיחת וואטסאפ** → וואטסאפ נפתח עם ההודעה כתובה → שולחים → **סימון כנשלח**
סוגר את אבן הדרך.

### עריכת הנוסחים

מסך **הודעות** מאפשר לערוך כל נוסח, לראות תצוגה מקדימה מול תיק לדוגמה,
ולחזור לנוסח המקורי. אין צורך במפתח ואין צורך בפריסה.

הקבצים ב-`config/messages/` הם ברירת המחדל שמגיעה עם הקוד. עריכה במערכת
נשמרת כדריסה במסד הנתונים, ו"חזרה לנוסח המקורי" מוחקת אותה. כך שתי הדרישות
של סעיף 9 מתקיימות: גם קבצים ניתנים לעריכה, וגם עריכה בלי מפתח.

### משתנים

כותבים אותם בסוגריים מסולסלות: `{{שם_פרטי}}`, `{{יעד}}`, `{{שעת_סגירת_צקאין}}`.
הרשימה המלאה מופיעה במסך ההודעות, ולחיצה על משתנה מוסיפה אותו לנוסח.

שלושה מהם מגיעים ממשתני סביבה ולא מהתיק: `AGENT_NAME` לחתימה, `AGENCY_NAME`
לשם העסק, ו-`AGENT_EMERGENCY_PHONE` למספר החירום שנשלח לפני היציאה.

**משתנה שאין לו ערך לא נעלם בשקט.** הוא נשאר גלוי בטקסט, מדווח בחלונית,
וכפתור וואטסאפ חסום עד שמטפלים בו. עדיף שהסוכן יראה `{{שעת_סגירת_צקאין}}`
מאשר שהלקוח יקבל "הצ'ק-אין נסגר בשעה ." ריקה.

### עברית ודו-כיווניות

סעיף 14 מזהיר מזה במפורש, ולכן זה מטופל בשלוש רמות:

- **קידוד.** הטקסט עובר `encodeURIComponent`, שמייצר UTF-8 תקין. הבדיקות
  מוודאות שפענוח חוזר מחזיר בדיוק את אותו טקסט, כולל שורות חדשות ותווים
  כמו `%`, `&`, `#` ו-`+`.
- **פיסוק שקופץ צד.** כל ערך לטיני או מספרי שנכנס למשפט עברי נעטף בתווי
  בידוד כיווניות בלתי נראים (U+2068 / U+2069). ערך בעברית בלבד נשאר נקי.
- **סוף שורה.** שורה שנגמרת במספר ואחריו נקודה מקבלת סימן RLM. שורה בעברית
  טהורה לא מקבלת — אין טעם לזהם טקסט שהסוכן עוד יעתיק ויערוך.

**מה שעדיין לא נבדק: מכשיר אמיתי.** האפיון אומר "לבדוק מוקדם על מכשיר
אמיתי", וזה נכון. בדקתי את הקידוד, את הפענוח ואת בניית הקישור בדפדפן, אבל
לא פתחתי וואטסאפ אמיתי בטלפון. **שלחו הודעה אחת לעצמכם לפני שאתם שולחים
ללקוח**, ותראו שהפיסוק במקום.

## פתיחת תיק

סעיף 4 אומר מילה במילה: *"אם יצירת תיק דורשת מילוי 20 שדות, המערכת תינטש
תוך שבועיים."* הטופס הראשון שבניתי היה בדיוק 20 שדות.

מדדתי את הזמן בפועל — 33 שניות לתיק מלא עם ארבעה נוסעים — אבל המספר הזה
מטעה: זה רובוט שמקליד בלי לחשוב, בלי לקרוא תוויות, בלי לחפש נתון במייל
ובלי לטעות. ומעבר לזה, **סעיף 4 לא מדבר על שניות אלא על נטישה.**

הבעיה האמיתית הייתה שהטופס ביקש דברים שברגע התשלום עוד לא ידועים: שש
מתוך עשרים השדות היו חברת תעופה, מספרי טיסה ושעות נחיתה — נתונים שחוזרים
מהספק אחר כך.

**עכשיו גלויים שבעה שדות**, וכולם ידועים בוודאות ברגע שהלקוח משלם: שם,
טלפון, יעד, שני תאריכים, שדה היעד ומחיר. פרטי הטיסה והכסף מקופלים ואפשר
להשלים אותם מהתיק בכל שלב. שדה היעד נשאר חובה כי בלעדיו אי אפשר לדעת
באיזה שעון לחשב את הצ׳ק-אין לטיסת החזור.

תיק שנפתח בלי טיסה מציג בראשו בדיוק אילו אבני דרך ממתינות למידע החסר.

### לקוח חוזר

"לקוח חוזר" הוא אחד ממקורות ההגעה שציינתם, ובשבילו כל הפרטים כבר במערכת
— כולל הדרכונים. הקלדה מחדש שלהם היא גם בזבוז זמן וגם מקור לטעויות
בשמות, שבשדה התעופה עולות כסף.

הקלדת השם מחפשת לקוחות קיימים. בחירה באחד מהם ממלאת את הפרטים ומציעה
להעתיק את הנוסעים מהתיק הקודם, דרכונים כלולים. אם התיק הקודם נסגר,
מספרי הדרכון כבר נמחקו (סעיף 10) ומועתקים רק השמות והתוקף — וזה עדיין
חוסך את רוב ההקלדה.

| | לפני | אחרי |
| --- | --- | --- |
| שדות גלויים | 20 | **7** |
| לקוח חדש, ללא נוסעים | 11 שניות | **5** |
| לקוח חוזר, כולל 4 נוסעים ודרכונים | 33 שניות | **5** |

המספרים נמדדו באותה אוטומציה ובאותה מהירות הקלדה, כדי שההשוואה תהיה
הוגנת. אדם אמיתי יהיה איטי יותר — אבל היחס נשמר.

## מה שנמצא כשבדקתי את המסלול של הסוכן מקצה לקצה

לפני שהתחלתי בשלב 5 עברתי על המסלול האמיתי: לפתוח תיק דרך הטופס, לנהל
אותו, לשלוח ללקוח. התברר שהמערכת יודעת ליצור ולעקוב, אבל כמעט לא יודעת
לערוך — ושתי חורים בדיוק היו חוסמים שבוע עבודה אמיתי.

**אי אפשר היה להזין נוסעים בכלל.** לטופס לא היה שדה, ולא היה שום מסך
להוסיף אותם אחר כך. כל תיק שנפתח דרך המערכת נולד בלי נוסעים — ומשם נשברה
שרשרת שלמה:

- בדיקת תוקף הדרכון (סעיף 5) לא יכלה לפעול לעולם
- "קליטת פרטי נוסעים" לא נסגרה לעולם, כי כלל הסגירה דורש שיהיה לפחות נוסע אחד
- `{{נוסעים}}` נשאר ריק, ולכן **ערכת מסמכי הנסיעה נחסמה לפני שליחה**
- "פרטי דרכון" לא הופיע ללקוח בעמוד שלו

**אי אפשר היה להזין מספר הזמנה.** רכיב נוצר עם תיאור וספק, ואחר כך ניתן
היה רק לשנות סטטוס או למחוק. ה-PNR — הדבר שהלקוח מחפש בעמוד שלו כשהוא
עומד בדלפק — לא היה יכול להיכנס לשום מקום.

שניהם נסגרו. הזנת נוסעים כוללת נרמול השמות לאותיות גדולות כמו בדרכון,
הצפנת מספר הדרכון, תצוגה ממוסכת עם פענוח לפי בקשה מפורשת, ושמירה על כך
שתמיד יש בדיוק איש קשר אחד — תיק בלי איש קשר הוא תיק שאי אפשר לשלוח אליו
כלום.

## עמוד הלקוח

עמוד web בקישור אישי, בלי התחברות, שנשלח בוואטסאפ — סעיף 8.4. לא אפליקציה.

מה שהוא מציג משתנה לפי שלב הנסיעה:

- **לפני היציאה:** ספירה לאחור, מה נשאר מהלקוח (יתרת תשלום, פרטי דרכון,
  החלטת ביטוח, צ'ק-אין שלא בוצע), פרטי הטיסות, ומה כבר סגור.
- **בזמן הנסיעה:** ראש העמוד מתחלף למספר החירום של הסוכן, כקישור חיוג,
  ולפרטי טיסת החזור.
- **אחרי החזרה:** הודעת "ברוכים השבים" עם תזכורת לדווח על תקלות, כי יש
  חלונות זמן להגשת בקשת פיצוי.

**השלב נגזר מהזמן ולא רק מהסטטוס במסד.** הסטטוס מתקדם ב-job היומי, ולקוח
שפותח את העמוד בשלוש לפנות בוקר אחרי ההמראה לא אמור לראות ספירה לאחור
שלילית.

העמוד הוא גם כלי מכירה: כל רכיב upsell שהוצע ולא נסגר מופיע כשורה פתוחה עם
כפתור שפותח וואטסאפ לסוכן עם הודעה מוכנה.

### מה אסור שיצא ממנו

זה ה-URL היחיד במערכת שפתוח לאינטרנט, והמסד שמאחוריו מחזיק מספרי דרכון,
עלויות ספקים ורווחים. לכן `publicView.ts` בנוי כ**רשימה לבנה מפורשת**: אין
שאילתה שמחזירה תיק ואז מסתירה שדות בתצוגה, יש שאילתה שבוחרת מראש רק את מה
שמותר. הוספת שדה למודל לא יכולה לדלוף לכאן בשקט.

הבדיקות אוכפות את זה: הן מפענחות את מספר הדרכון האמיתי ומוודאות שהוא לא
מופיע בתשובה, בודקות שרשימת המפתחות במודל התצוגה היא בדיוק המותרת, ושתיק
סגור מפסיק להציג כלום.

### הקישור

טוקן אקראי קריפטוגרפית באורך 192 ביט, ולא נגזר מה-id של התיק — מזהה רץ היה
מאפשר לנחש תיקים של לקוחות אחרים. הקישור עצמו הוא הסוד.

הוא מגיע ללקוח דרך המשתנה `{{קישור_ללקוח}}` בתבניות ההודעות, ואפשר גם לשלוח
אותו נקודתית ממסך התיק. אם לקוח העביר אותו הלאה — כפתור "החלפת הקישור"
הורג את הישן ומייצר חדש.

בלי `PUBLIC_BASE_URL` אין דרך לדעת תחת איזה דומיין המערכת רצה, ולכן הודעות
שמכילות את הקישור **ייחסמו לפני שליחה** במקום לשלוח כתובת שבורה.

## אבטחה

האפיון אומר "בלי הרשאות ובלי חלוקת תיקים" (סעיף 3), כלומר אין משתמשים ואין
תפקידים. הוא לא אומר שהמערכת פתוחה: היא מחזיקה מספרי דרכון, תאריכי לידה
וטלפונים. לכן:

- **מנעול אחד.** סיסמה משותפת, עוגייה חתומה ב-HMAC, תוקף 30 יום. הכל חסום
  חוץ מ-`/login`, `/api/health` ו-`/api/jobs/`.
- **מספרי דרכון מוצפנים** ב-AES-256-GCM ונמחקים בסגירת תיק, ולעולם אינם
  מגיעים לעמוד הלקוח.
- **השרת לא עולה** בפרודקשן בלי כל המפתחות, ולא עם סיסמה קצרה מ-12 תווים.
- **ה-job היומי** דורש טוקן, והשוואת הטוקנים והסיסמה נעשית בזמן קבוע.
- **המערכת מסומנת `noindex`** ולא תופיע במנועי חיפוש.

- **האטה על ניסיונות כניסה**, משותפת לכל המופעים. חמישה כשלונות חוסמים,
  וההשהיה גדלה: דקה, חמש, חמש עשרה, שעה. בזמן חסימה גם הסיסמה הנכונה
  נדחית.
- **כותרות אבטחה**: מסגור חסום, MIME sniffing חסום, ו-referrer מוגבל.
  עמוד הלקוח מקבל `no-referrer` מחמיר יותר, כי הטוקן נמצא בכתובת עצמה —
  בלי זה הוא היה יכול לדלוף ב-Referer לכל קישור יוצא.

### מה שנבדק, ומה שנשאר סיכון מקובל

**Server Actions.** ב-Next.js הן endpoints של HTTP, והחשש היה שפעולה מוגנת
תהיה ניתנת להפעלה דרך הנתיב הציבורי `/c/`. בדקתי מול ה-manifest של הבנייה:
28 פעולות, **כולן ממופות לנתיבים שה-middleware חוסם**. לעמוד הלקוח אפס
פעולות בגרף שלו, ו-Next מנתב פעולה רק לנתיב שרשומה בו.

**מה שנשאר סיכון מקובל:**

- ההאטה היא לפי כתובת. תוקף שמחליף כתובות יעקוף אותה. חסימה גלובלית הייתה
  מאפשרת לו לנעול את הסוכנים עצמם מחוץ למערכת, וזו עסקה גרועה יותר.
  ההגנה האמיתית היא אורך הסיסמה, ולכן בפרודקשן נדרשים 12 תווים לפחות.
- הודעות שגיאה מהשרת מוחזרות כלשונן לדפדפן. הן יכולות לחשוף פרטי מסד
  במקרה קצה — אבל היחידים שיכולים להפעיל פעולות הם שני הסוכנים המחוברים.
- אין יומן פעולות. אם תרצו לדעת מי סימן מה ומתי, זה שינוי נפרד.
- הגיבוי הוא באחריות ספק מסד הנתונים. ב-Neon יש point-in-time; ב-Fly צריך
  להגדיר `fly postgres backup` בעצמכם. **תבדקו שזה עובד לפני שנכנסים לעונה.**

## מה אפשר לערוך בלי מפתח

שלושה קובצי נתונים ב-`config/`, כפי שהאפיון דורש:

- `config/templates/leisure-package.json` — אבני הדרך: כותרת, קהל, עוגן, היסט,
  חלון התראה, חסימות והשלמה אוטומטית. הוספת תבנית = הוספת קובץ ורישום שלו
  ב-`src/lib/milestones/template.ts`. כל תבנית מאומתת בעלייה, ושגיאה בה נופלת
  מיד עם הודעה בעברית ולא בשקט.
- `config/data/airline-checkin-rules.json` — חלונות הצ'ק-אין לפי חברת תעופה.
  **המספרים כאן הם ניחוש סביר ולא מקור אמת — צריך לעבור עליהם.**
- `config/data/airports.json` — אזור הזמן של כל שדה. שדה שלא מופיע כאן ייחסם
  ביצירת תיק, כדי שלא תיווצר הנחת אזור זמן שגויה.

## החלטות שהתקבלו

**סטאק.** Next.js + Prisma + PostgreSQL, שכבה אחת שתשרת בהמשך גם את עמוד
הלקוח (סעיף 10). אין Tailwind ואין ספריית תאריכים — RTL וזמנים נכתבו ידנית
כי שניהם קריטיים ולא רציתי להסתיר אותם מאחורי הפשטה.

**אזורי זמן.** כל זמן שנתון בשעון שדה תעופה נשמר כזוג (שעה מקומית נאיבית,
אזור IANA) וה-UTC נגזר ממנו. חלונות הצ'ק-אין נגזרים משעון שדה היציאה.
מטופלים גם השעה שאינה קיימת במעבר לשעון קיץ והשעה הכפולה בחזרה ממנו.
הבדיקות ב-`tests/zones.test.ts` כוללות טיסה מבנגקוק, שבה חישוב בשעון ישראל
היה נותן תשובה שגויה ב-5 שעות.

**הצמדה לשעת עבודה.** אבני דרך ברזולוציית ימים מוצמדות ל-09:00 שעון ישראל
(ניתן לשינוי בתבנית), אחרת התור מתמלא בפריטים ב-23:40 רק כי כך יצא מההיסט.
ההצמדה לעולם לא מקדימה את העוגן עצמו — תיק שנפתח ב-13:00 לא נולד עם אסמכתא
שעברה את מועדה ב-09:00, ו"ברוכים השבים" לא נשלח לפני הנחיתה.

**תיק שנוצר מאוחר (סעיף 14).** אבני דרך שנולדות אחרי מועדן מסומנות ומקובצות
לשורה מתקפלת אחת במקום 12 שורות אדומות. שני סוגים **אף פעם** לא מקובצים,
כי הם בדיוק הכשלים הכספיים מסעיף 2: בעיית תוקף דרכון, ומועד ביטול חינם שעבר.

**ביטוח.** אבן הדרך של סגירת הביטוח לא ניתנת לוויתור. הכפתור פותח בחירה בין
נרכש דרכנו / הלקוח סירב / נרכש מחוץ לסוכנות, וההכרעה נשמרת עם תאריך.

**דחייה זמנית.** גם היא מחייבת סיבה, לא רק ויתור — סעיף 12 דורש ששום אבן דרך
לא תיעלם מהמסך בלי טיפול או סיבה.

**רכיב שהלקוח סירב לו** נספר כ"סגור" לצורך חסימת המסמכים. האפיון מדבר על
`confirmed` או `cancelled` בלבד, אבל בלי זה הצעת upsell שהלקוח דחה הייתה
חוסמת את שליחת המסמכים לנצח.

**פרטים אישיים.** מספרי דרכון מוצפנים ב-AES-256-GCM עם מפתח מהסביבה, ונמחקים
בסגירת תיק. תאריכי התוקף נשארים, כי הם נדרשים להזמנה הבאה ואינם מזהים
כשלעצמם.

## תשובות שהתקבלו לסעיף 13
